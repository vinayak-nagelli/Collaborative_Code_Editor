[24] 7. Realtime Collaboration: Non-Negotiable Behavior
[25] Each collaboratively open file uses a real Y.Doc in server memory.
[26] Clients send binary Yjs update deltas; they do not treat the whole file string as the live synchronization payload.
[27] Yjs updates are merged with CRDT semantics; do not introduce last-write-wins logic.
[28] Awareness carries cursor/selection/presence information.
[29] Only opening/closing a file changes Y.Doc ownership/ref counts; high-frequency updates should use peek/non-owning lookup behavior.
[30] MongoDB persistence is debounced rather than performed on every keystroke.
[31] Version restore must merge through the CRDT path instead of blindly overwriting the live editor.
[32] Any feature that modifies code in a file that may be open collaboratively must respect the Y.Doc as the live source of truth.
[33] 8. Current Security Model and Constraints
[34] JWT is stored in an HTTP-only cookie; client JavaScript should not receive the token directly.
[35] Project REST routes use membership/owner/editor middleware; the server derives roles from the database.
[36] Socket connections authenticate at handshake and collaboration events re-check project membership.
[37] Project collaboration room capacity is enforced server-side (current maximum 4).
[38] Terminal commands use an explicit binary allowlist, shell=false, 30s wall-clock timeout and 200KB output cap.
[39] Terminal commands execute against a scratch copy rather than the application source tree.
[40] Credential-bearing Git remote URLs are a documented MVP caveat; do not design a public production system around plaintext secrets in MongoDB.
[41] Before exposing execution to untrusted internet users, replace the current trusted-user terminal model with real container isolation / resource limits.

[61] 16. Rules for Antigravity While Coding
[62] First inspect the existing files and execution path relevant to the feature. Do not guess where logic lives.
[63] Prefer extending existing controllers, services, stores and components instead of replacing working modules.
[64] Keep API logic in backend routes/controllers/services and keep React components focused on UI/state orchestration.
[65] Use the existing authorization middleware for every project-scoped endpoint.
[66] Use MongoDB for durable business records; use Socket.IO/Yjs for live state and ephemeral presence.
[67] For collaborative file changes, never make a direct REST full-file overwrite the source of truth when the Y.Doc is open.
[68] For AI-generated code, use proposal → verification → human approval → CRDT application.
[69] Do not add an AI provider directly into many frontend components; create an AI service boundary.
[70] Keep execution isolated and preserve the current terminal security assumptions. Avoid enabling arbitrary shell execution.
[71] Add migrations/backward-compatible defaults for new MongoDB fields. Existing projects must keep working.
[72] When adding a new persistent domain object, define: schema/model, controller/service, routes, frontend store/state, UI, permissions, and tests as applicable.
[73] After changing realtime code, test concurrent edits, reconnects, file close/open, restore-version and presence cleanup.
[74] After changing search, Git or terminal services, test interaction with the shared scratch workspace and live Y.Doc.
[75] Never mark a feature complete unless it is actually wired end-to-end and tested.
[76] 17. Definition of Done for Any New Feature
[77] ☐ User can reach the feature from an intentional UI entry point.
[78] ☐ Frontend state is managed consistently with existing Zustand/service patterns.
[79] ☐ Backend API/socket path exists where required and validates authentication + project permissions.
[80] ☐ Persistent data has a Mongoose model or a deliberate reason why persistence is unnecessary.
[81] ☐ Errors are handled and visible to the user in a consistent way.
[82] ☐ Feature works with existing projects and does not break collaboration.
[83] ☐ Feature has a minimal test path or manual verification checklist.
[84] ☐ Documentation/readme is updated when setup, events or security behavior changes.
[85] ☐ No mock/stub is presented as production behavior unless explicitly labeled as future/mock.
[86] 18. Non-Goals / Things Not to Build Yet
[87] Do not rebuild the editor or replace Monaco unless there is a demonstrated requirement.
[88] Do not replace Yjs/CRDT collaboration with a naive database-save-on-every-keystroke approach.
[89] Do not implement every startup idea in one sprint. Prioritize the final-year MVP around requirements, tasks, contribution evidence, QA and AI.
[90] Do not build a full video-conferencing stack before the core engineering workflow is stable.
[91] Do not expose arbitrary command execution to the public internet without real container isolation.
[92] Do not use lines-of-code as the main employee performance score.
[93] Do not create a giant single React component or giant Express controller for all new modules; split by domain.
